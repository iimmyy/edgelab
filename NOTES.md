# Design notes

## Release 1

Setting up a connection and actually forwarding bytes are two different jobs, so I keep them apart. Round-robin picks the first target, and if that one doesn't come up, I work through the rest before any forwarding kicks off. One deadline covers DNS and all the attempts together, and each target gets its own smaller deadline inside that.

Moving the data is Tokio's bidirectional copy. It keeps half-close working the way it should and lets me size the buffer for each direction on its own. A permit sticks with the forwarding task until that task either wraps up or gets cancelled. The Go fixture then on the far end says who it is, echoes back whatever you send it, and sits on the EOF marker until the client half-closes. The verifier waits very very patiently for the whole response before it calls anything.

Every listener in an app has the same admission state. That stays consistent across reloads, and it stays true for sessions that were already running when the reload hit. Limits are still process options though. There's also a hard ceiling of 1,024 sessions covering old and new config at the same time. Config itself maxes out at 1 MiB, 64 apps, 256 listener ports, and 64 targets per app.

New listeners get bound before I flip the active view over. If validation blows up, or the bind fails, nothing changes and the old view stays. Streams already in flight keep whatever backend they landed on. Candidate config loads get two seconds and run outside admission so they can't starve anything out. One validation runs at a time, with one pending request that can get replaced. Only the newest generation anyone asked for is allowed to activate, so if that newest candidate turns out bad, the active view just stays where it is rather than dropping back to something older (wow so impressive!!!). The lab can stall validation on purpose to show that admission keeps running and that stale results get tossed.

DNS is Hickory, async, 256-entry response cache, 32 in-flight requests per DNS connection. I skipped the OS hostname lookup most noteably due to the blocking resolver jobs hanging around long after the connection deadline is gone. The literal addresses don't touch DNS at all. If a lookup hands back a pile of addresses I'll try 16 of them max, still inside the target deadline. DNS is shared here so of course its not full tenant isolation.

The global session ceiling, the per-app permits, the capped message sizes and the capped client workload are lab limits, and I'd rather say that out loud than hide it lol. Kernel TCP buffers and listen backlogs are extra memory on top. Resource tests look at process RSS and descriptor count, and they don't try to chase down every kernel allocation. Logging is JSON going into a lossy 128-message queue that feeds stderr (no I didn’t have a stroke its actually called stderr… derrrrr). If the sink backs up, logs get dropped and forwarding keeps running, and once the sink then recovers, the periodic observations say how many went missing. Shutdown gets a deadline that covers draining and a best-effort log flush together. The logging thread never drags shutdown out, which neither does filesystem work I've already walked away from.

The verifier caps concurrency at 256, payloads at 1 MiB, and attempts at four million. What it spits out includes every failure and every timeout, nothing rounded off (as far as im aware). Churn runs under the admission ceiling on purpose, because the client can see EOF before the server task has finished cleaning up after itself. Saturation gets tested on its own. A benchmark passing just means I got a full measurement out of it. Zero errors isn’t reallyyy the bar… I mean maybe but If something broke and I can't say why, the release isn't ready to go out of course.

Connection diagnostics keep DNS and TCP setup apart, and they keep my own deadlines apart from OS errors. A deadline with SO_ERROR=0 only means the kernel hasn't told me about an error yet. But it could still mean the handshake failed. Direct and proxied workloads run back to back on the same box, with the same backend, client, payload, concurrency and duration. So take that how you will.

## Release 2

The fixture owns four loop files, the LVM identities attached to them, two network namespaces, and workload processes it tracks separately. It won't go near a host that isn't marked, and it won't go near a loop device whose backing path isn't on that list (until I break something). Once setup finishes you can run it again and nothing bad happens. If setup gets cut off halfway through making the disks, it stops and waits for someone to look, instead of guessing whether some volume already sitting there is safe to format. Cleanup checks ownership first and leaves everything else alone. (hopefully)

Objects are immutable and named by SHA-256. Writing one goes: sync the temp file, link it in without stomping an object that's already there, drop the temp name, sync the directory, then acknowledge. The service re-checks the mount and the owner marker on every single request. The client makes its own content and keeps its own list of acknowledged hashes, so it's never just taking the service's word for it. Application and management listeners are separate, and only the application path actually gets blocked on the base network.

The growth controller grabs one nonblocking process lock. It checks that SQLite is actually on WAL with FULL sync, writes down the operation ID and the absolute target size before it touches anything, that way im not gaslighting myself.. but then it brings the LV size and the filesystem size in line. If it dies right after `lvextend`, that same target is still sitting there pending, so the restart finishes the `resize2fs` instead of piling another increment on top. The watched version polls every two seconds with a matching cooldown, and when growth can't happen it exits with the error written down. LVM's 4 MiB extent rounding, the allocation cap and the backing reserve are all spelled out. systemd supervision for workloads is a later-release thing, and these fixture processes already live through a controller restart on their own.

Breaking the network and fixing it are two separate operations. On this kernel, pulling the only address off an interface, or taking the interface down, kills its route too, so the repair has to put both back. The fake MTU fault keeps its size filter on while I check the smaller tunnel MTU. These are replays I wrote myself :D

## Release 3

The worker is Go (not the ancient board game… and not an English verb indicating movement), It looks over an OCI fixture I own, then hands the layers off to a separate extraction process that's rooted at the mounted thin volume, so extraction has nowhere to wander off to (becuase it really wants to GO.. heh) Once the layers are down the origin gets sealed read-only, and every operation after that gets handed its own writable thin snapshot. Nothing ends up sharing a writable device. Readiness means there's an active device sitting there, so a worker without one doesn't get to go ahead and claim it's ready. Run the same operation twice and it keeps the snapshot identity it already had instead of minting a fresh one. ***Identity theft is NOT a joke ~~Jim!~~ ehm.. Go!***


The CLI puts mutations in a line, one at a time. If another caller turns up while something's running it gets `worker busy` handed back and can try again once the current operation is done. No queueing!

I'd honestly rather support a narrow thing properly than a wide thing badly, so the supported subset is small and written down: Linux/ARM64, one to four gzip tar layers, root-owned regular files and directories, and normal or opaque whiteouts. Links, special files, PAX attributes and privileged modes all get rejected flat out. Limits are 16 MiB per blob, 64 MiB of expanded content, 4,096 entries, a 512 MiB blob cache and 128 retained operations…. blob 

The test suite builds its own image store and works out its own expected hashes, so it's never checking the worker against numbers the worker handed it (confirmationnnnn biasssss). It covers whiteouts, corrupt and missing and unsupported input, archive containment, copy-on-write isolation that actually gets verified rather than taken on faith O7, concurrent requests, 18 separate interruption points, and the data and metadata capacity guards.

The worker fixture stands on its own. `worker.py down` rips out that worker's pool and state and leaves the networking and storage fixture completely alone. That's the same separation rule from the worker contract, and this is where it stops being a promise.

This just proves it's filesystem preparation and an activation. Again obviously not VM runtime lol.

## Approved contracts for later releases

**Worker.** Write down the intended absolute size and the stable resource identity before you cause any effect. After something gets interrupted, go look at the actual external resource and reconcile instead of assuming. SQLite settings get checked, never assumed. Workloads get their own supervised units, and restarting management can't kill them or leave duplicates behind. Object writes are single-owner and immutable, with contents and directory metadata both synced before anything gets acknowledged.

**Restoration.** The harness turns publication off, explicitly. One restartable admin operation pulls the accepted history off both routing nodes, reconciles revisions and tombstones, quarantines anything unknown or conflicting, and saves one shared result. Both nodes have to acknowledge the reconciled incarnation and fence the old publication credentials before anything publishes again. A partial recovery blocks, then picks back up by operation ID. 

**Routing.** Workers own instance authority. Updates get authenticated. Tombstones and endpoint reservations stay for the whole lab lifetime. Full snapshots get reconciled on a schedule, and every proxy subscriber has one pending complete view waiting for it. Defaults are 4,096 lifetime records per worker and a 16 MiB edge view. Room for deletion gets reserved at admission, so when space gets tight the system turns down new additions rather than chopping up state it's already holding. Worker reconciliation time stays separate from proxy delivery time.

**Proxy cache.** Order goes: write the temp file, sync it, rename inside the same directory, lose my mind, sync the directory, then activate. If any step falls over, the active in-memory view stays put and persistence gets flagged as degraded. On restart the cache gets validated and stays marked stale until it's refreshed. If dynamic state is missing or broken, it does not slide back to static routes. Cached routes that still work don't time out on their own (yep they get their OWN time-out corner!!!). A retired endpoint won't belong to some other instance for the lifetime of the lab. Fencing a publisher's credentials does nothing to caches that are already disconnected.

**Independence.** Routing and proxy are separate supervised processes and neither one cares what order they shut down in. Management and workload units are the same deal. The verifier owns its own expectations rather than borrowing route-selection or recovery decisions off the thing it's supposed to be checking.

Release 2 is where WireGuard and data-volume recovery get proven. Release 3 is where OCI materialization and real snapshots landed. Release 4 adds distributed routing and the operational failure cases. Release 5 pulls all of it together into the capstone. Private checkpoints let me poke at each working release without stopping for an approval pause. Optional extension lanes stay out of the core. Process-kill, whole-VM interruption and physical-host guarantees are different problems and I keep them that way.
